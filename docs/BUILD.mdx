# Сборка UI-Kit и оптимизация

## Команды и результаты

- `npm run build` — собрать npm-библиотеку в dist.
- `npm run check-package` — собрать библиотеку и проверить её публичные импорты и CSS.
- `npm run build:report` — собрать библиотеку и вывести размеры групп файлов.
- `npm run build-storybook` — собрать статическую документацию в storybook-static.
- `npm run storybook` — открыть среду разработки Storybook на порту 6006.
- `npm test` — выполнить браузерные тесты в Chromium.
- `npx playwright install chromium` — установить браузер перед первым запуском тестов.

Сборка библиотеки и сборка Storybook решают разные задачи. В npm-пакет отправляется dist, а Storybook остаётся отдельным сайтом документации. Публикация не выполняется этими командами.

## Как работает сборка библиотеки

Сначала запускается tsup с конфигурацией из tsup.config.ts. Входы — src/index.ts, src/components/Button/Button.tsx и src/components/Input/Input.tsx. Имена выходов заданы ключами index/button/input: PascalCase исходников не меняет публичные импорты `@microfronts/ui/button` и `@microfronts/ui/input`.

TypeScript/JSX превращается в JavaScript. Форматы esm и cjs дают файлы .js и .cjs. Опция dts создаёт .d.ts и .d.cts для TypeScript-потребителей. В package.json условные exports выбирают код и типы для import/require. Индекс дополнительно сохраняет Badge и Panel; внутренние хуки и примитивы не экспортируются.

Включены minify, treeshake и splitting. Для сгенерированных внутренних JS-chunks moduleSideEffects отключён в соответствии с контрактом пакета, поэтому лишние импорты без используемых bindings удаляются. CSS и внешние зависимости сохраняют побочные эффекты. Минификация уменьшает текст JavaScript. Tree shaking удаляет неиспользуемый код там, где это возможно. Общие части нескольких входов попадают в chunk-файлы; поэтому один button.js — не вся реализация Button. Подпуть должен поставляться вместе с соответствующими chunks. Исходные карты .map помогают отладке.

Зависимости из external остаются импортами: React, React DOM, React Hook Form, Base UI и утилиты классов. Их отсутствие внутри JS-файлов уменьшает дублирование, но не означает нулевую стоимость зависимостей у приложения. React и RHF подключаются через совместимые peerDependencies; остальные runtime-пакеты перечислены в dependencies.

После tsup команда build:css запускает Tailwind CLI. Вход src/styles.css импортирует общую основу src/styles.base.css и содержит явные @source только для компонентов; stories/test/spec исключены. Общая основа сохраняет Tailwind, tw-animate-css, служебный CSS shadcn и неизменяемую тему. Tailwind генерирует CSS для обнаруженных классов, затем минифицирует его. scripts/relative-css.mjs применяет общий PostCSS-плагин: числовые px в декларациях и @media превращаются в rem с делением на 16. Исходные примитивы при этом не меняются.

CSS подключается статическим импортом из ESM/CommonJS сборки (banner в tsup). Сборщик приложения обрабатывает и извлекает CSS. Подпуть `@microfronts/ui/styles.css` сохранён для совместимости; вручную импортировать его не нужно. Чистый Node без CSS loader больше не может непосредственно выполнять эти входы; для SSR требуется обработка CSS сборщиком. `sideEffects: ["**/*.css"]` сообщает сборщику потребителя, что CSS-импорты нельзя безусловно удалять как неиспользуемые. Стилизация включает Tailwind Preflight, влияющий на страницу.

## Как работает Storybook и Playwright

.storybook/main.ts выбирает истории из src/components и MDX из src/docs, подключает addons и Vite. preview.tsx импортирует отдельный вход .storybook/styles.css с общей темой, добавляет переключатель темы и декоратор .dark. Активные истории покрывают все четыре публичных компонента: Button, Input, Badge и Panel.

Истории Button/Input показывают состояния; Badge/Panel документируют существующий API. У Badge/Panel нет интерактивных состояний disabled/error, и их mf-\* оформление остаётся ответственностью приложения.

В vitest.config.ts два проекта. Первый преобразует Storybook stories в тесты через addon-vitest. Второй выполняет src/components/**/\*.test.tsx и src/form/**/\*.test.tsx. Оба используют провайдер @vitest/browser-playwright с Chromium; дополнительно playwright.config.ts запускает @playwright/test для реальных страниц Storybook (npm run test:playwright).

Storybook play-функции проверяют сценарии документации. Самостоятельные тесты через vitest/browser выполняют реальные движения мыши, клики, ввод и клавиатуру через браузерный драйвер. Это особенно важно для CSS :hover. См. [API взаимодействий Vitest](https://vitest.dev/api/browser/interactivity).

Zod и resolver заранее указаны в optimizeDeps второго проекта, чтобы их поздняя обработка Vite не перезапускала уже исполняющийся тест.

## Что уже оптимизировано

- Отдельные входы позволяют использовать Button напрямую, а ESM помогает сборщику приложения удалять ненужные экспорты. Фактическое дерево зависимостей следует проверять в сборке потребителя.
- Общие chunks уменьшают повторение реализации между входами.
- Зависимости не вклеены в каждый компонент.
- Tailwind сканирует явно перечисленные источники, а не весь репозиторий.
- Пакет содержит dist; тесты, истории и инструменты разработки не являются JS-кодом поставки.
- Служебные экспорты закрыты через package.json exports и проверяются check-package.

## Следующие возможности оптимизации

1. **Изоляция CSS реализована.** Библиотека и Storybook используют общую основу, но разные источники классов. .storybook/styles.css включает истории, src/docs и preview; в npm они не сканируются.
2. **Анимации сохранены.** tw-animate-css остаётся по решению пользователя. Служебный CSS shadcn также сохранён для data-вариантов установленных примитивов.
3. **Измерять пакет в приложении.** Маленький entry-файл не показывает стоимость Base UI и утилит. Отдельная сборка потребителя с одним Button даст полезнее данные о загрузке, чем сумма всего dist.
4. **Решить, нужны ли sourcemaps в поставке.** Они занимают около 27 КБ до сжатия, но полезны для отладки. Исключение из npm уменьшит архив, обычно не меняя JS, загружаемый приложением.
5. **Сохранять CommonJS до решения о совместимости.** Отказ от него уменьшит объём установки, но сломает require-потребителей; это изменение контракта, а не бесплатная оптимизация.
6. **Рассматривать Storybook отдельно.** Предупреждение Vite о chunks свыше 500 КБ относится в том числе к docs/axe/инструментам Storybook. Для ускорения сайта можно отдельно оценить addons и загрузку документации. Отключение accessibility-проверок ради меньшего числа не улучшает библиотеку.

Статус каждого пункта указан отдельно; возможности оптимизации потребителя не означают обнаруженных ошибок библиотеки. Текущая конфигурация и результаты сборки — источник фактических сведений. Общая документация инструмента: [tsup](https://tsup.egoist.dev/).

CSS сократился на 119 байт: большинство utilities историй используются и в компонентах. Разделение предотвращает попадание нового оформления документации в npm-пакет. Классы, переданные потребителем через className, по-прежнему должен генерировать его собственный CSS-пайплайн; демонстрационные классы не являются API пакета.

В tsup сохранён Rollup tree shaking: эксперимент без него не устранил лишние импорты и увеличил CommonJS. Точечная настройка moduleSideEffects удаляет только неиспользуемые импорты сгенерированных JS-chunks, не отключая CSS. scripts/finalize-build.mjs устраняет повторную хвостовую ссылку на ту же sourcemap в tsup 8.5; несовпадающие ссылки вызывают ошибку. onSuccess запускает обработку и в watch-режиме. check-package проверяет единственность ссылки и корректность JSON карты.

Проверка потребителя собирает только Button из корня библиотеки и проверяет, что RHF не остаётся в импортах, а CSS сохраняется. Все публичные подпути ESM/CommonJS остаются прежними.

### Загрузка Storybook

Локальный Chromium, отдельный чистый контекст для Canvas и Docs кнопки, статический HTTP-сервер без сжатия, измерение PerformanceResourceTiming после networkidle: Canvas 2059487 байт, Docs 2408826 байт. Это декодированный объём загруженных ресурсов, не gzip и не размер npm. Ошибок JavaScript нет.

Крупнейшие ресурсы: общий iframe JS 1136270 байт, axe 587045 байт в Canvas, docs components 566551 байт в Docs. Предупреждение о chunks свыше 500 КБ оставлено видимым: это upstream-модули документации и доступности. Разбиение ради порога предупреждения не уменьшает суммарную загрузку; addons и accessibility-проверки сохранены. Замер не доказывает проблему скорости на реальном хостинге, поэтому сетевые оптимизации требуют отдельного измерения с компрессией и кешированием.
